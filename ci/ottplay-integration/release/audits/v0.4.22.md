# OTTPlay LG 0.4.22 candidate audit

## Device test evidence

The exact installed 0.4.21 package reached live playback, then retained a terminal HLS window failure. A separate manual selection reported a selected-playlist request timeout before decoding. Background suspension was also observed and is distinguished from foreground playback failure.

## External compatibility reports known at release time

A bounded inspection of the actual Home source returned a master and a selected live playlist containing one ten-second segment. Two selected responses ten seconds apart had the same sequence, Cloudflare DYNAMIC and no-store headers, with no Age header. The proxy's configured upstream polling interval can exceed ten seconds, so this does not establish a stopped playlist or a cache fault.

A second bounded probe consumed the complete first transport segment. Server logs confirmed the same client identity and successful first download, but the next segment download did not complete and was cancelled approximately 55 seconds after starting. Native requests for that next segment then timed out. This is separate upstream/downloader evidence; removing a client polling delay does not repair an unavailable server object. Backend remediation and physical acceptance remain required.

## Compatibility tiers, and what moved

The producer previously blocked while feeding the whole segment, then waited up to three additional seconds before refreshing the manifest. Remove that additional wait after progress. A live window that has passed the next required segment needs a fresh same-source decoder session rather than continuation with missing references. Only that precise positive window-slip, and a live playlist observed not to advance beyond its existing bounded deadline, receive the trusted recoverable outcome. The broader window-error class remains insufficient for retry. Seek refusals, sequence corruption and overflow do not authorize recovery.

Existing retry budgets, original catalogue identity, pause/suspend cancellation and admission controls remain authoritative. No auto-next behavior is introduced. Startup/resident-media tests and the bounded cold-entry rules from 0.4.21 remain applicable.

An additional remote parity regression covers Back from a completed catalogue: the interface retained valid entries, but RPC capabilities omitted Categories while the catalogue waited for UI reentry. Remote snapshots may reuse only a matching completed retained outcome; reading them must not alter the UI, persistence or producer. Incomplete, failed, stale or differently bound outcomes remain insufficient. A real RPC/admission/failure regression also found stale continuity ownership after Back: the accepted explicit selection now rebases that exact retained generation before recording the selected item. Reads, rejected/background selections and automatic recovery do not perform this transfer.

## Release configuration

Record exact-source tests and package identity before installation. Physical startup, sustained picture and sound, and same-channel recovery require television acceptance. The prior package is not treated as accepted merely because host tests or position counters passed. Release flags and shipping qualification gates remain unchanged.

## Known issues at release, with provenance

The backend downloader has separate evidence of missing ready media after a slow upstream transfer. The candidate does not claim to repair that upstream. A sustained physical playback check after server remediation remains required; source-owned retry is bounded and does not guarantee uninterrupted playback on an unavailable feed. Native codec admission and the pre-existing queued/accepted high-water model remain unchanged.
