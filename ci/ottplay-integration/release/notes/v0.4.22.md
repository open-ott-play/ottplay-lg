# OTTPlay LG 0.4.22 candidate

Refresh an external live HLS playlist immediately after feeding new media. Apply the normal polling delay only when the playlist has no new media, instead of adding up to three seconds after each completed segment.

When a live window has already advanced beyond the next required segment, or has stopped advancing beyond the existing bounded deadline, reopen the same selected channel through the existing bounded retry policy and a fresh decoder session. Do not splice dependent pictures across missing media or advance to a different channel. Pause, suspension, source changes and admission restrictions still cancel recovery. Invalid sequences, seek refusals and overflow retain their existing failure policy. No-progress recovery does not shorten its existing detection deadline.

Keep a previously completed catalogue available to remote reads and channel selection after Back, without reopening the channel-list screen. Reuse it only while its source/profile and generation still match; partial and failed scans do not gain completion authority.

Retain the startup, duration-backed resident-media and bounded cold-entry corrections from 0.4.21, together with System television and LG Channels support.

The installed 0.4.21 did not pass physical playback acceptance. Its retained trace reports an HLS window failure after startup, and a separate channel selection timed out before decoding. This candidate does not claim that one correction resolves every upstream timeout. Host checks, ARM package verification and physical-TV acceptance must be recorded separately. A local `ARM_PROFILE=tvdev` package is functional validation only, not a stable or shipping performance qualification.

Package SHA-256: `__IPK_SHA256__`.

After downloading the release assets into one directory, verify them with `shasum -a 256 -c ottplay-lg-0.4.22.sha256` before installation.
