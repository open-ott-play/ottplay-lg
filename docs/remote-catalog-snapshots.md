# Remote catalogue snapshot contract

A successful first categories request captures an immutable catalogue view. Its continuation token and channel-page tokens derived from it keep the captured total, row order, IDs, display names, numbers and loading flag. Appending rows, enriching presentation metadata or finishing discovery does not change those pages. A new categories request without a token captures the latest view, including newly discovered rows and the current completion state.

The existing protocol and error schema remain unchanged. A retained token does not bypass current runtime, provider/profile, catalogue generation, Favorites or organisation authority, availability, expiry, or playback policy. For ordinary catalogue rows, before starting a selected item the player checks the current prepared ID and MediaLocator against a private SHA-256 binding captured in the snapshot. Favorites retain their exact portable identity and existing source/proof checks through the ordinary PendingPlay rebind. The acknowledgment still identifies the selected snapshot row with its original ID/name/number. The existing pending-request and final-admission checks remain responsible for later source changes. A changed or missing target is rejected; appending an unrelated row is allowed.

Selecting a category also checks that its captured canonical ID still exists as that same ID before admitting the Saved writer. A label alias must not redirect a disappeared canonical category. The existing acknowledgment-time selection checks remain intact.

An explicit successful temporary-list shuffle or reset starts a new read context: its old read tokens and cached snapshot are retired. This does not cancel an already admitted exact playback request or reset the token serial. Ordinary catalogue batches do not perform this retirement.

Successful reads renew the 120-second idle lease. Lookup, Play and refused reads do not renew it. Expired or capacity-evicted tokens use the existing rejection behavior; the controller can obtain a new categories snapshot. There is no unbounded automatic retry.

The ledger and its cache retain at most two distinct snapshot families, at most 64 read receipts, at most 200,000 query-index entries, and at most 32 MiB of accounted owned allocation capacity. Shared snapshots and query buffers are counted once for bytes. A new successful read can evict the oldest other snapshot family as a unit. Capability/status refresh replaces an unpinned cache or declines to retain its candidate; it does not evict active read families merely because another batch arrived. Continuation/channel/play lookup uses the retained snapshot before any current-cache work.

These are retained allocation bounds, not a process RSS or peak-memory promise. Building a candidate snapshot, hashing a locator, serializing a response and temporary owned values can coexist with retained state. Snapshot construction is still subject to the existing bounded source catalogue plus the snapshot's own accounted-size check. The wire response retains the existing 200-row and 1 MiB limits. No artwork, full entry metadata or duplicate media URL/request is retained for each read token.
